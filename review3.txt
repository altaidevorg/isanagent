This pull request implements a background job management system, introducing a 'waiting' state for tool execution, clarification ticket handling, and automatic job resumption. It adds telemetry support for background_job_id across various events and introduces a new terminal UI pane for monitoring and interacting with background jobs and notifications. The reviewer provided several actionable suggestions: propagating errors in the job resumption flow, refactoring duplicated metadata and notification logic into helper functions, adopting a unified data structure for the background jobs UI to improve maintainability, and simplifying struct field access in sub-agent tools.

The error from rx.await is only logged, but the resolve_and_resume_job function doesn't propagate it. If ResolveClarificationTicketFull fails, the job remains in a 'waiting' state, but the user's reply that triggered this flow is effectively consumed without resuming the job. This could lead to a confusing state for the user.

Consider changing resolve_and_resume_job to return a Result and handle the error in the calling functions (try_resume_background_job_from_ticket and try_auto_resume_waiting_job). This would allow for more robust error handling, perhaps by not consuming the user's message if the resume operation fails, or by notifying the user of the failure.

Comment on lines +2195 to +2233

The logic to determine the selected item's chat_id when handling the Enter key in the BackgroundJobs focus mode is brittle. It relies on the count and rendering order of three separate lists (notifications, background_jobs, agent_tasks). If the rendering order in background_pane_paragraph changes, this logic will break, potentially causing incorrect behavior like jumping to the wrong chat. This same issue applies to the up/down arrow key handling.

A more robust approach would be to create a unified data structure in the App state for the items in this panel. For example:

enum BackgroundPanelItem {
    Notification(crate::memory::NotificationRecord),
    Job(crate::memory::BackgroundJobRecord),
    AgentTask(AgentTaskEntry),
}

impl BackgroundPanelItem {
    fn chat_id(&self) -> &str {
        match self {
            Self::Notification(n) => &n.chat_id,
            Self::Job(j) => &j.chat_id,
            Self::AgentTask(t) => &t.child_chat_id,
        }
    }
}

// In App struct:
// pub background_panel_items: Vec<BackgroundPanelItem>,
By populating and operating on a single, unified list, both the rendering and event handling logic would be more maintainable and less prone to bugs.

This logic for extracting the background_job_id from metadata is repeated in multiple places across the codebase (e.g., in execute_tool_call_with_activity, run_reasoning_loop, and subagent.rs). To improve maintainability and reduce code duplication, consider creating a helper function.

For example, you could add a function to crate::bus:

pub fn get_background_job_id(metadata: &std::collections::HashMap<String, serde_json::Value>) -> Option<String> {
    metadata
        .get(METADATA_BACKGROUND_JOB_ID)
        .and_then(|v| v.as_str())
        .map(|s| s.to_string())
}
Then you could simply call crate::bus::get_background_job_id(&inbound.metadata) where needed.
